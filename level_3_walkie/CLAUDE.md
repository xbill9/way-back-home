# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Biometric Security System — a FastAPI + Google ADK backend streaming video/audio to the Gemini Live API, with a React/Vite frontend.

Commit directly to `main` and push — no feature branches, no PRs. Deps install into the active interpreter via `./scripts/install_deps.sh`; no virtualenv.

## Support scripts

Every `.sh` entrypoint starts with `#!/bin/bash`, `set -euo pipefail`, and `cd "$(dirname "${BASH_SOURCE[0]}")"`, so it operates on **this** directory no matter where it is invoked from. (They used to hardcode `cd $HOME/way-back-home/level_3_gemini` and act on the sibling copy.) Keep that preamble on any new script — the `cd` in particular, since an unguarded one used to let `build.sh` overwrite a `Dockerfile` in the caller's working directory.

Secrets are never passed on a command line or written world-readable: `~/gemini.key` and both generated `.env` files are `chmod 600`, and anything that prints `.env` pipes it through a `sed` redaction.

## Commands

- `make test` — `python -m pytest`. See "Tests can't fail" below.
- `make lint` — `ruff check .`, `ruff format --check .`, then `cd frontend && npm run lint`. Check-only; there is no `make fmt`. Run `ruff format .` to actually format.
- `make frontend` — `npm ci && npm run build` (**`ci`**, not `install`: the Dockerfile builder does the same, so the image and your machine build the identical locked tree. Run `npm install` by hand when you mean to bump `package-lock.json`). Required before the backend can serve the SPA; `main.py` mounts `frontend/dist` at `/` and only warns if it's missing. `frontend/node_modules` is absent on a fresh clone, so `make lint` fails until this runs.
- `make run` (8080, real API) · `make mock` (8080, offline fake server) · `make adk` (8000, ADK dev UI) · `make testadk` (interactive ADK CLI).
- `make verify` — `scripts/verify_setup.sh`; checks project, APIs, Python deps, and both `.env` files. Exits non-zero on failure, so it can gate a build.
- `make record` (billed, records mic+camera) → label `ground_truth.json` by hand → `make eval` → `make submission` builds the one `.tar.gz` to upload to the EAP. Captures default to `~/eval-captures`; `EVAL_CAPTURE_DIR` overrides. `make eval` exits non-zero on a failed session, so it can gate a bundle. Details, including what the anomaly checks look for, in `evals/README.md`.
- `make build` / `make deploy` delegate to `./build.sh` / `./deploy.sh` — one definition each, no duplicated gcloud invocation in the Makefile. Both derive `PROJECT_ID` from `~/project_id.txt` and default `SERVICE_NAME`/`REGION`/`IMAGE_PATH`; override via the shell. `make endpoint` shares the same `SERVICE_NAME`/`REGION` defaults.

Use `make mock` for frontend work — it replays `mock/mock_audio.pcm` and a canned tool call, so it costs nothing.

## Models

Never use 2.0 models (deprecated); 2.5 or later only. Production is **`models/walkie-talkie`**, the latency-optimised half of the Live audio EAP; it replaced `gemini-3.1-flash-live-preview`. `models/clever-chatter` (the reasoning half) is selectable with `MODEL_ID` and is the only model that gets a `thinking_config`. `live_models.get_model_id()` inspects `sys.argv` and falls back to `gemini-2.5-flash` under `adk run`, because Live-only models 404 on `generateContent` — so `make testadk` exercises a different model than production. That fallback now triggers for *any* Live-only model, not just the default one; an explicit `MODEL_ID` pointing at another Live model used to slip past it into the 404 it exists to prevent.

EAP access is granted **per GCP project**: here that is **`comglitn` (project number `1056842563084`)**, and `~/gemini.key` holds that project's `EAP` key. A key from anywhere else gets the socket refused with `1008 ... not found for API version v1alpha, or is not supported for bidiGenerateContent` — which is an *access* error wearing a not-found costume, since `gemini-3.1-flash-live-preview` keeps working on the same key and both API versions fail identically. The previous key (`aisprint-491218`, not allowlisted) is at `~/gemini.key.pre-eap-backup`. `make verify` warns when the active gcloud project is not the EAP one; it cannot see which project the *key* belongs to, so the definitive check is `python -m pytest test_live_connection.py -s` (billed, one connect).

**The repeat run is fixed, and the fix came from the wire trace.** `SCHEDULING=SILENT` on EAP models, paired with `main.py` asking for the spoken confirmation on the first call (`STORM_NUDGE_AFTER`, which defaults to 1 when the tool result is silent). They are one design, not two knobs — SILENT alone is a mute scanner, which is exactly how it shipped once.

**What was happening**, traced with `ADK_DEBUG=1` (unmutes ADK's own logging, including the responses it sends):

```
RECV tool_call
RECV generation_complete      <- 4ms
RECV turn_complete            <- turn over, nothing spoken
SEND function response        <- 5ms, correct id
     ~628ms
RECV tool_call                <- a NEW turn, same decision, calls again
```

Every repeat is a **complete turn**, and **our own answer starts the next one**: under `BLOCKING` the tool result prompts the model to continue, and walkie-talkie continues by re-reading the same video and re-calling instead of speaking. So a "storm" was N full request/response cycles that we were driving, one per answer. `SILENT` means "add the result to context, do not trigger generation" — no trigger, no next turn, no loop.

That trace also **falsifies the assumption ADK is built on**. `gemini_llm_connection.py` says *"Gemini 3.x Live does not emit turn_complete until it receives the tool response"*, and yields tool calls immediately to avoid a deadlock. Measured on walkie-talkie: turn_complete arrived **before** our response **38 times out of 38**, median 4 ms after the call. The shim is still required (ADK selects that path by model name, and these ids do not match), but not for the reason ADK gives.

| | calls/scan | spoke | accuracy | scan → voice |
|---|---|---|---|---|
| `BLOCKING` (previous default) | 18 over 10 scans | 10/10 | 10/10 | 1.95 s med, 2.90 s worst |
| **`SILENT` + confirmation prompt** | **1 × 10** | **10/10** | **10/10** | **1.73 s med, 2.21 s worst** |
| `gemini-3.1-flash-live-preview` | 1 × 10 | 10/10 | 10/10 | 1.48 s |

Confirmed in the browser under deliberate background noise: five scans, one call each, every confirmation spoken.

Everything else verified along the way, so nobody re-litigates it: the client sends one `{"type":"text"}` per command (the frame carries `heard`, which caught a real phantom — room noise heard as `'scan photos'`, since the wake word matches `scan` as a substring); ADK answers **every** call in ~8 ms with the matching id (26/26, zero unanswered); the wire shows one `LiveServerToolCall` message per call with unique ids, 1:1:1 with our logs; and during a run we transmit nothing between the answer and the next call, not even video.

Detection is unaffected across models (scan → `report_digit` p50 0.65-0.71 s), which is why this presents as "the digits are right but it feels laggy": the digit reaches the UI in well under a second either way, and it is only the spoken confirmation that waits behind the repeat run. The one-call line in rule 5 is EAP-gated (`_SCAN_INDEPENDENCE` in `agent.py`) so the prompt stays byte-identical to `level_3_new` on every other model.

Verified against the real endpoint on 2026-08-12: opening line, `report_digit` firing with a single `match` frame, and silence after the tool result. Details and the gaps in `GEMINI.md` → "What is verified, and how". Note `./testmodels.sh` lists models supporting `bidiGenerateContent` — the EAP models are not expected to appear there, so absence is not evidence of missing access.

Everything model-dependent lives in `backend/app/biometric_agent/live_models.py`, and two ADK gaps are why it exists. ADK 2.6.3 recognises Live models **by name**:

- `LLMRegistry` only resolves `gemini-*`, so `Agent(model="models/walkie-talkie")` raises `Model ... not found` at import. `build_live_model()` returns a `Gemini` **instance** for EAP ids (accepted by `Agent(model=...)`) and a plain string for everything else.
- `_is_gemini_3_x_live()` means "starts with `gemini-3.` and contains `-live`", which these ids fail. It gates the split `send_realtime_input(audio=/video=)` fields, single-shot input transcription, and — the one that matters — **yielding tool calls as they arrive instead of buffering them until `turn_complete`**. With async function calling a `report_digit` can arrive *after* `turnComplete`, so buffering would strand it. `EapLiveGemini` sets the flag on the connection ADK just built. It is a subclass, not a patch; delete it when ADK learns these ids.

**Tools carry no `response_scheduling` at all, on any model** (`agent.py: _build_tools()`), so every model gets the same bare `BLOCKING` declarations `level_3_new` sends: call → result → one spoken `"[Number] digits."`, which is the flow instruction rule 6 describes.

The claim this repo used to make — clever-chatter *requires* `NON_BLOCKING` and hard-errors on `BLOCKING` — **is false as of 2026-08-13**. clever-chatter refuses the field itself: `1007 Function response scheduling is not supported for this model.`, socket closed at setup, every session dead. So the EAP gate that existed to keep clever-chatter working was the only thing breaking it, and `MODEL_ID=models/clever-chatter` could never have run. Either the EAP moved or the invite was wrong; `supports_blocking_function_calls()` survives in `live_models.py` with no callers, as the record of the claim.

It carried `SILENT` on both EAP models, read as the protocol form of the instruction's "after the tool result: STAY SILENT". That is not what `SILENT` does — it means the result never triggers generation, and since the model emits the call with no speech of its own, **nothing was left to say the confirmation**: the scanner detected digits in total silence. Measured with `scan_accuracy.py`, 5 digits held 8 s each:

| scheduling | detected | spoken | calls | notes |
|---|---|---|---|---|
| `SILENT` | 3/3 | **0** | 3.7/trial | downlink 12.9 kbit/s — the greeting and nothing after |
| `WHEN_IDLE` | 5/5 | 4/5 | 6.4/trial | talks, then loops: the result prompts a turn, it re-calls off its own result. "Four digits." spoken 4× for one hand — `main.py`'s 1.5 s dedup hides the calls from the client, not the speech |
| unset (`BLOCKING`) | 5/5 | **5/5** | 1.4/trial | p50 0.65 s, each confirmation once |

This was drift from `level_3_new`, which the EAP port was only supposed to change the model in — the instruction text is byte-identical between the two, and `level_3_new` passes bare callables. `test_agent.py` now pins the value per model, since nothing caught it shipping.

Three EAP config rules, all of them "do not set the field": affective dialogue is **removed** from the API; proactive audio is permanently on and `proactiveAudio: false` is a **hard error**; `RESPONSE_MODALITY=TEXT` is unsupported (`main.py` logs an error and forces AUDIO — read the output transcript instead). Turn coverage defaults to `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO` (as it already did on 3.1), so every frame sent is billed and contextualised; the `VIDEO_FPS` clamp is the only bound on that.

**`interaction_status` cannot be surfaced through ADK**, despite the EAP follow-up recommending it as the definitive idle signal. ADK rebuilds every server message into an `LlmResponse`, which is `extra="forbid"` and has no such field, so the value is dropped before `main.py` sees it — installing the private `google_genai-2.14.0` wheel changes nothing, and that wheel is both a downgrade from the pinned 2.17.0 and mTLS-only (so unavailable to the Docker build). Nothing here needs it: no client code ever treated `turn_complete` as an idle signal. See `GEMINI.md` → "Live audio EAP".

## No monkey patching (removed)

`backend/app/patch_adk.py` is gone. ADK 2.6.3 handles Gemini 3.x Live natively — it detects the model via `_is_gemini_3_x_live()` and routes audio to `send_realtime_input(audio=)`, images to `video=`, and single-part text Content to `text=`. Do not reintroduce the patches; fix the caller instead.

The one thing this changed for callers: **`LiveRequestQueue.send_realtime()` accepts only `types.Blob`.** Text must go through `send_content()` — use the `send_text_stimulus()` helper in `main.py`. Passing a bare string raises a Pydantic `ValidationError` (the old patch hid this with `model_construct`).

The one deliberate exception, and the shape any future one should take: `live_models.EapLiveGemini` subclasses `Gemini` to set `_is_gemini_3_x_live` on the connection ADK hands back, because ADK derives that from the model name and the EAP ids do not match. Nothing in ADK is rebound, non-EAP models never construct the class, and it is deleted the moment ADK recognises the ids. A subclass at the seam is not a monkey patch; reaching into `google.adk` and reassigning its functions is.

## ADK 2.x compatibility

Pinned at `google-adk==2.6.3`. Nothing here is deprecated, and that is checkable: `python -W error::DeprecationWarning -m pytest -q` reports zero ADK warnings — re-run it after any ADK bump.

Four rules keep it that way. 2.0 moved agents onto a graph engine, so:

- Use the plain `Agent`. Custom `BaseNode` subclasses and `_run_async_impl()` / `generate_content()` overrides are **silently bypassed** — no error, just no effect.
- Never hand-append events to the session; `run_live()` owns it.
- The Runner sets **`auto_create_session=True`**. Do not reintroduce a hand-rolled `get_session`-then-`create_session`.
- Pass `user_id`/`session_id` to `run_live()`. The `session=` parameter is deprecated.

`RunConfig.save_live_model_audio_to_session` **does not exist**, despite ADK's own `run_live()` docstring naming it; the real fields are `save_live_blob` / `save_live_audio`. Full breaking-change table in `GEMINI.md` → "ADK 2.x status".

## Environment

`GOOGLE_API_KEY`, `GEMINI_API_KEY`, and `GEMINI_KEY` must all be set to the same value — every config path sets all three. `GOOGLE_GENAI_USE_VERTEXAI=False` (Gemini API key path, not Vertex, despite the GCP setup). Secrets live outside the repo in `~/project_id.txt` and `~/gemini.key`; `runadk.sh` generates `backend/app/biometric_agent/.env` from them. There is no `.env.example`.

Installing deps: **always go through `./scripts/install_deps.sh`** (`--dev` also installs `requirements-dev.txt`). A bare `pip install -r requirements.txt` or `uv pip install -r requirements.txt` hard-fails with `ResolutionImpossible` / `No solution found`.

`requirements.txt` pins `websockets==17.0.1`, above the caps `google-adk` (`>=15.0.1,<16`) and `google-genai` (`>=13.0.0,<17`) declare. Those bounds are "last version we tested", not a real incompatibility — every websockets API these libraries call exists in 17.0.1 — so `overrides.txt` overrides them. `uv` applies it with `--override`; pip has no equivalent (`--constraint` can only tighten a bound), so the script installs the tree without websockets and then forces the pin with `--no-deps`. Both routes resolve to the same 56-package set.

Do **not** "fix" this with a bare `pip install -r requirements.txt --no-deps` — `--no-deps` applies to the whole command and skips every transitive dependency (pydantic, starlette, sqlalchemy…), leaving an app that can't import. `pip check` reporting the websockets conflict afterwards is expected.

`Dockerfile` passes `--override overrides.txt`, and `init.sh` calls the script, so `make build`, `cloudbuild.yaml`, and a fresh `./init.sh` all work. `init.sh` no longer runs `pip install google-adk --upgrade`: that ignored the `google-adk==2.6.3` pin and silently re-resolved `websockets` back below 16. If the Live socket misbehaves, drop the override and pin `websockets==15.0.1` to test whether it's the cause.

`main.py` hard-exits if `GOOGLE_API_KEY` is unset **only under `python main.py`** — the `sys.exit(1)` sits behind `if __name__ == "__main__"`. On import it logs two CRITICAL lines and continues (the comment promises it "raises error" otherwise; nothing does), which is what makes the offline test suite possible. `PORT` reads Cloud Run's `$PORT` (default 8080). `VIDEO_FPS` (default 1.0 — the Live API's documented max — honoured up to 5.0) is interpolated into the agent instruction, so backend and prompt stay in sync; `main.py` and `agent.py` declare it separately and the two ranges must stay identical. It was briefly **hard-clamped** at 1.0, so `VIDEO_FPS=2` silently did nothing; that is fixed, because a knob that ignores you is worse than no knob. Raising it does not buy accuracy — `scripts/scan_accuracy.py` scored 10/10 at both 1.0 and 2.0 under identical blur, with 1.0 the *faster* of the two (0.68s vs 1.80s median). `HEARTBEAT_INTERVAL` defaults to 10.0, clamped 5.0–30.0.

Four more knobs, all read once at import:

- `RESPONSE_MODALITY` (`AUDIO` default, or `TEXT`) — the modality used to be *inferred* from `"live" in model_name`, which was right for `gemini-3.1-flash-live-preview` only by coincidence (it is half-cascade, not native-audio) and would have silently muted the demo on a name without the substring. It is a deployment decision now — and on the EAP models it is not even that: AUDIO is the only supported modality, so `TEXT` logs an error and is overridden.
- `THINKING_LEVEL` (`MINIMAL` default) — only reaches the model under `MODEL_ID=models/clever-chatter`. `RunConfig` has no `thinking_config` field; the only route into a live session is the agent's `generate_content_config`, which `Gemini.connect()` copies into the `LiveConnectConfig`.
- `VIDEO_WIDTH` / `VIDEO_HEIGHT` / `JPEG_QUALITY` (640×480, q60) — capture size and quality, **shipped in the `config` frame** so the client has no second copy. `scripts/scan_accuracy.py` measured 5/5 at every setting — 640×480 q60 at 128.6 kbit/s, 480×360 q50 at 77.3, 320×240 q40 at 40.1 — and **that table got the default wrong**: 480×360 shipped on it and made real accuracy visibly worse, because every fixture has a hand filling the frame while a hand at arm's length loses its fingers first. **Don't trade resolution for bandwidth** — the uplink is ~77% microphone (256 kbit/s of raw PCM, uncompressible).
- `ALLOWED_ORIGINS` — comma-separated allowlist checked at the WebSocket handshake. **CORS does not apply to WebSockets**, so this is the only gate in front of a public `--allow-unauthenticated` URL. Empty means accept anything and logs a warning at startup; `deploy.sh` passes it through and warns again if you deployed without one.
- `HEARTBEAT_ENABLED` (default on) — the heartbeat sends `CONTINUE_SURVEILLANCE` as a **real user turn**, not a transport keepalive, so the model can answer it out loud. It only fires when the client has gone quiet. It existed because the pre-EAP model was not proactive; the EAP models have proactive audio permanently on and may simply decline a nudge they judge irrelevant, so an unanswered heartbeat is not necessarily a fault.
- `PORT` — see above.
- `EVAL_CAPTURE_DIR` — unset (off) by default. Points at a directory to record real sessions into for the EAP eval bundle: input/output audio, JPEG frames, timestamped events, and a `ground_truth.json` template. It records the microphone and camera, which is why nothing turns it on implicitly, and why `.gcloudignore`/`.dockerignore` exclude `eval-captures/` in case it is ever pointed inside the repo. `make record` / `make eval` / `make submission` are the loop; see `evals/README.md`.
- `RAW_TRANSCRIPT_DEBUG` — **temporary**, default on, delete with the diagnostic it serves. Logs every transcription chunk (`repr`, plus `live_session_id`/`interaction_id`/`model_version`) before the `finished` gate, to catch a recurrence of the 2026-08-12 transcript splice.

**There is no canned audio greeting.** `main.py` used to open every session by reading `mock/mock_audio.pcm` and sending it wrapped in a synthetic `serverContent.modelTurn`, which is indistinguishable from real model output to the client — a recording presented as the Live API, in a demo about the Live API. It also only existed locally, since the Dockerfile never copies `mock/`. The opening line now comes from the model: the `"Neural handshake"` stimulus forces the first turn and the agent instruction ends with `Say "Scanner Online." to initialize.` `tests/test_ws_session.py` pins this — don't reintroduce it.

## Tests

`pytest.ini` sets `testpaths = tests backend/app/biometric_agent`, so `make test` collects only the hermetic suites: **57 tests, no API key, no network, no charge — and they can fail.** Report a green `make test` as verification of the protocol layer only.

Specifically, the suites stub `runner.run_live()`, which means **session creation, resumption and teardown are never exercised** — `make test` passes whether or not they work. Anything touching the session lifecycle or `RunConfig` has to be checked against the real API with a WebSocket client; that is how `auto_create_session` and `context_window_compression` were verified.

**`scripts/scan_accuracy.py` is the only thing here that measures the model rather than the plumbing**, and it needs no human: it drives the real endpoint with the fixture hands in `tests/fixtures/hands/` (640×480 JPEG q60, the exact format the browser sends), a `{"type":"text"}` frame in place of saying "scan", and scores every `report_digit` against a known count. One billed session per run. `--matrix` sweeps nine conditions; `--min-rate` makes it a gate. The fixtures were generated with `gemini-3.1-flash-lite-image` and **every count was verified by eye before committing** — generate the input, never the expectation. `scripts/telemetry_report.py` renders any run as a standalone HTML report. See `@docs/testing-strategy.md` → Tier 6.

`tests/test_ws_protocol.py` covers the frame-by-frame wire contract; `tests/test_ws_session.py` covers whole-connection behaviour — origin policy, the audio-rate handshake, clean shutdown, and the two regressions above. `tests/test_eval_capture.py` covers the eval bundle (recorder, scorer, packager) and, through the same in-process transport, that the endpoint feeds the recorder and flushes it on disconnect; the model half of a recording — output audio, transcription chunks, tool calls — is unreachable there because `run_live()` is stubbed. `backend/app/biometric_agent/test_live_models.py` covers model selection: the EAP feature matrix as assertions, the `adk run` fallback, and the two ADK gaps (`build_live_model` returning an instance, `EapLiveGemini` forcing the 3.x flag). All of it is offline reasoning about config — none of it proves the EAP endpoints accept what it produces.

The **root-level** `test_*.py` files are excluded from default collection and are manual smoke checks, not tests. `test_ws_backend*.py` wrap their body in `try/except Exception: print(...)`, so they pass no matter what, and need a server already on `ws://127.0.0.1:8080`. `test_live_connection.py` makes a **real billed Live API call** and builds its `genai.Client` at *import*, which is why it used to abort collection for the whole session; it no longer swallows its exception, because proving EAP access is the entire reason to run it. It honours `MODEL_ID`, so it is the one-call check for "does this key reach `models/walkie-talkie`". Run these by explicit path when you actually want them.

`tests/` drives the real WebSocket endpoint in-process: `main.py` imports fine with no key (the `sys.exit(1)` is guarded by `if __name__ == "__main__"`), and `runner.run_live()` is the only call that reaches Gemini, so stubbing it makes the whole endpoint testable offline. See `@docs/testing-strategy.md` before adding tests — it documents the fixtures, what's deliberately not covered, and the shutdown bug that forces `ws_connect` to suppress exceptions on teardown.

## Style

`ruff.toml` in **this directory** (not the git root, `~/way-back-home` — that scoping is what keeps the sibling `level_3*/` copies out of the rule set) pins the rule set. Both ruff steps of `make lint` pass — **a red ruff run is now a real regression**, not pre-existing noise. Read the comments in `ruff.toml` before widening `select` or removing an `ignore`; each entry records why. In short: `E4/E7/E9`, `F`, `I`, `UP`, `B`, `ASYNC`, `SIM`, `RUF`, minus `ASYNC230`/`ASYNC240` (one-shot startup reads, not per-request I/O) and `SIM102` (defensive `hasattr` probing on ADK event shapes). `E501` and `W` are left out because `ruff format` owns line length and whitespace, and agent.py's instruction prompt is one long string literal no formatter can wrap.

The exclude that matters: **`extend-exclude = ["*.md"]`**. Ruff 0.16 formats Python fenced blocks inside Markdown, so without it a bare `ruff format .` rewrites the code samples in `GEMINI.md`, `.gemini/skills/live/SKILL.md`, and `docs/article-*.md`. With it, `ruff format .` is safe.

The third `make lint` step is `cd frontend && npm run lint`, which needs `frontend/node_modules` — run `make frontend` first or that step fails on a fresh clone.

`.claude/settings.json` runs a `PostToolUse` hook that `ruff format`s any `.py` file after a Write/Edit, so Python files change on disk after an edit.

The one non-default JS rule is `frontend/eslint.config.js`: `'no-unused-vars': ['error', { varsIgnorePattern: '^[A-Z_]' }]`. No TypeScript, no Prettier.

## Other gotchas

- **Never `useRef(new Thing())` when the constructor owns a resource.** `useRef` evaluates its argument on *every* render and discards the result. `AudioStreamer` opened an `AudioContext` in its constructor, so the page leaked one per render — one per second, from the metrics sampler — none of them closed. Chrome caps concurrent contexts at about six, and past that `new AudioContext()` throws inside `AudioRecorder.start()`, where it is caught and logged as a failed microphone: a later round would silently have no audio, cleared only by a page reload. Measured before and after in the browser: 6 contexts per 6 idle seconds, now 0. Both audio objects are built on first use, and `AudioStreamer` defers its context to `ensureInitialized()` — which also suits the autoplay policy, since by then a user gesture has happened.
- **Per-session measurements reset on `onopen`, not on mount.** `BiometricLock` stays mounted across rounds, so the metrics ref survives them. Round 1 ends on a `match` whose audio never arrives (the socket closes first), leaving `lastMatchAt` set — and round 2's first audio chunk then measured `speak` from round 1's match, across the entire gap between rounds. It presented as `speak` going red on every run after the first. Latencies above 10 s are also discarded outright: the Live session would have timed out long before, so that is a stale timestamp rather than a slow model.
- **A new round must mint a new `session_id`.** `auto_create_session=True` creates a session when one is missing and **resumes** it when it isn't, so reconnecting with the same id continues the previous conversation. `BiometricLock.jsx` used to derive the id per *mount*, but the component stays mounted across rounds — so round 2 opened mid-scan with "Five digits." instead of "Scanner Online.", and round 3 answered once and went silent for the rest of the session. `startRound()` now mints a fresh UUID and passes the URL straight into `connect(url)`. Verified against the real API: same id → no greeting, fresh id → "Scanner Online."
- **Continuous speech in the room silences the scanner outright** — zero tool calls, zero transcripts, downlink from ~83 kbit/s to 1.8. VAD reads a continuous voice as a user turn that never ends, so the model never takes one. Measured with `scripts/scan_accuracy.py --noise chatter` (0/5); `--noise hiss` is the partial version (3/5). Vision is the robust half: blur, dim and backlit all scored 5/5, and only a near-black frame fails. If a live session feels broken while every component looks healthy, suspect the microphone before the camera.
- **The microphone is not streamed to the model by default.** Its only job is to catch the word "scan", and streaming raw PCM to do that costs 256 kbit/s — about two thirds of the uplink — while continuous audio is also what stops the model taking turns (measured 0/5 with speech in the room, against 5/5 for the identical prompts sent as text). `wakeWord.js` listens locally via the Web Speech API and sends the same `{"type":"text"}` frame the offline harness sends, which is the configuration already measured as the reliable one. Uplink drops from ~385 to ~128 kbit/s, all video. `?mic=stream` restores the old behaviour, `?mic=off` sends nothing, and anywhere `SpeechRecognition` is missing (it is Chrome/Edge only) it falls back to streaming rather than leaving the demo deaf. Caveat worth knowing: Chrome's implementation sends that audio to Google's speech service — not billed to the Live API key, but not on-device either.
- **A dropped Live session no longer ends the round.** The API can close with **1007** ("Request contains an invalid argument") mid-run, and ADK treats 1007 as fatal — no reconnect, the socket simply goes. It has not been reproducible outside a real browser session: eight scans over seventy seconds, four scans at 4 s spacing, and four overlapping scans landing mid-reply all ran clean against the same backend. So the client reconnects with a fresh `session_id`, up to three times per round; past that it stops, because if the API is rejecting something we send then retrying forever just repeats it, each attempt billed. The error handler now logs `code`/`status`/`details`/`response` and a traceback, since "invalid argument" never names the argument.
- **Telemetry resets at the start of every round, and `clear` in the Trace panel does it on demand.** The record otherwise spans every round since page load, so the reviewer drew several runs as one continuous session with the gaps between them flattened out — and a manual button is the kind of thing that gets forgotten mid-demo. Clearing publishes the emptied figures immediately as well as into the ref, because updating only the ref left the panel showing the old numbers until the next sampler tick, which reads as the button doing nothing.
- **The voice is pinned** via `speech_config` (`VOICE_NAME`, default `Charon`). Left unset the API picks one per connection, so the scanner sounded like a different character on every run.
- **One spoken "scan" must send exactly one scan, and the dedup key is the utterance, not the clock.** Chrome delivers an utterance repeatedly — interim results refined until the final one lands, all sharing a `results` index — and `wakeWord.js` used to filter those with a 1 s timer, which is not the same shape as the thing it filters. Measured in a real session: two `USER TEXT: scan` frames **1.03 s and 1.44 s apart**, each starting its own round of `report_digit` calls. That is the audible cost, because under `BLOCKING` the model may not speak until every call has round-tripped, so each extra call pushes the spoken confirmation back ~0.7 s: scan → voice runs **1.16–1.36 s when the model calls once and 1.63–2.97 s when it calls 2–3×**, while scan → `report_digit` (when the UI updates) stays 0.44–0.90 s throughout. Dedup is now by result index, with the timer kept as a second guard for a genuinely repeated utterance; the index resets on `onend`, since restarted recognition numbers from 0 again and a remembered index would swallow the first command after every restart. `node scripts/wake_word_check.mjs` pins both directions — firing twice for one utterance, and going deaf to a second one. Residual, not fixed: the model sometimes re-calls the same digit off its own continued video, which no client-side change can reach.
- **The wake word takes two frames before it sends the scan.** This is the fix for the misreads, and they were not perception errors at all. Captured frames from a real run (`DEBUG_FRAME_DIR`) show five fingers in frames 12–13, a fist in 16, one finger in 17 — and the four the user was holding in between exists in no frame at all. Every report that session matched what was genuinely in shot. At 1 FPS the shutter opens once a second and a pose held for less than that is invisible. Raising `VIDEO_FPS` fixes it by brute force and doubles the video uplink for the whole session (128 → 256 kbit/s); a burst spends two frames per scan (~51 kbit/s while actively scanning, nothing when idle) on the only frames that were ever going to decide the answer, because people pose and *then* speak. Frames go before the text on the same socket, so ordering guarantees the model has the pose before it is asked to count it. **Beware of concluding anything about frame rate from `scan_accuracy.py`**: it holds one static fixture per trial and is structurally incapable of seeing a sampling miss — that is exactly how "1 FPS and 2 FPS score the same" was measured and believed.
- **A scan waits for the model to stop talking, rather than cutting it off.** Sending a scan mid-reply interrupts the model: measured at six scans on 1.5 s spacing, five interruptions, only four of six replies finished. Nothing broke — every scan still produced a detection, no errors — but the scanner sounded clipped, which reads as a fault. `scanScheduler.js` holds a request only while the model is actually speaking and releases it on `turnComplete`, so silence still sends instantly and a mid-reply scan waits roughly as long as the reply has left (~1 s). Repeats collapse to one; a 2 s backstop covers a turn that never completes; a new session resets it. `node scripts/scan_queue_check.mjs` pins both failure directions — interrupting everything, and holding so long it feels laggy. `?interrupt=1` restores the interrupting behaviour for comparison.
- **`RESPONSE_MODALITY=TEXT` does not work on this model** and is forced back to AUDIO with an error. Measured: the model refuses it at setup and closes the socket with `1007 The requested combination of response modalities (TEXT) is not supported by the model`, so *every* session dies instantly. It was documented here as a supported option, which made it a trap. Read the output transcript instead — it carries the same words the audio does.
- **Don't replace the model's voice with browser speech synthesis.** It was proposed and rejected: local TTS would make the confirmations perfectly consistent and could even speak them *sooner* (a `match` frame carries the digit, so the client knows the line before the model has finished saying it). It is still wrong here. This demo exists to show the Live model driven through ADK, and a scanner that talks in the browser's voice is no longer demonstrating that. It would not even save bandwidth — the model generates and sends its audio regardless, and TEXT modality is refused at setup, so the audio arrives either way and would simply go unplayed. Live-model delivery varies; that is a property of the thing being demonstrated, not a defect to paper over.
- **The voice is pinned; the *delivery* is not, and the API offers no control over it.** Measured three ways when "different voice each time" was reported. (1) An invalid `VOICE_NAME` is refused with `1007 No matching speaker voice found`, so `speech_config` demonstrably reaches the API. (2) The **same sentence** across four sessions — the greeting — lands at 161–171 Hz median pitch, a 10 Hz spread: one voice. (3) **Different sentences** in the same sessions spread 160–226 Hz. So what a listener hears as a different voice is the model reading different words differently. Two attempted fixes measured and rejected: `temperature=0.15` moved a 40 Hz spread to 33 (noise), and forcing one uniform carrier phrase ("Digits: two.") moved 66 Hz to 50 — not worth changing the demo's script for. Browser TTS would fix it completely and is [rejected on purpose](#). Live-model delivery varies; that is a property of the thing being demonstrated.
- **A language selector proves the model is really being called.** Picked on the idle screen, sent as `?lang=` on the WebSocket URL — it has to be known before the socket opens, since `speech_config` is part of the Live connect config and cannot change mid-session. The backend sets `speech_config.language_code` and asks for the opening line in that language; the model translates its own confirmations, so no phrasebook is shipped that nobody here can check. Verified live: `en-US` → "Scanner Online." / "Three digits."; `es-ES` → "Escáner en línea." / "Tres dedos."; `ja-JP` → "スキャナー オンライン" / "3つ。" A recording cannot do that, which is the point — the demo otherwise looks identical whether it is driving the Live API or replaying a file. `LANGUAGES` in `main.py` is the single list, served through both the config frame and `/api/config`, so the menu cannot offer something the backend would reject.
- **`DEBUG_FRAME_DIR` writes every received JPEG to disk.** Off by default and never implicit — these are frames of somebody's room. It exists because every accuracy investigation here has run against fixture images (five clean, deliberate, hand-fills-frame poses) while the misreads happen on a real camera; two reported misreads failed to reproduce against the fixtures, which means the fixtures were the wrong thing to look at.
- **The opening line is pinned, not hinted.** The startup stimulus asks for the exact words (`Say exactly "Scanner Online." and nothing else.`) rather than sending `"Neural handshake"` and relying on the agent instruction's closing line, which is a hint the model varied between runs. Verified across four fresh sessions: identical wording each time, first audio at 1.02–1.31 s after connect. The voice is pinned separately via `speech_config`.
- **The startup overlay clears when the scanner speaks**, not after a fixed 5 s. Its own copy says "wait for audio confirmation", so it waits on the confirmation — the greeting arrives at ~1.1 s, so the fixed timer was about four seconds of dead air. Derived from the trace rather than an effect that clears a flag (setState in an effect is a cascading render), with an 8 s backstop for a session that never greets. Trace events publish immediately rather than on the 1 Hz sampler for the same reason: batching delay here is time spent staring at a loading screen.
- The overlay used to promise `"Biometric Scanner Online"` and the on-screen prompt used to say `Say "CALIBRATE" / "SCAN"`. Neither matched anything real — the agent says `"Scanner Online."` and nothing has ever recognised "calibrate", not the instruction and not `wakeWord.js`. Both now say what actually works.
- **The header shows the live model name**, from the server rather than a constant: `MISSION ALPHA` told a viewer nothing and could never go stale because it was never true. The name rides the WebSocket `config` frame *and* a plain `GET /api/config`, because the config frame only arrives once a round opens a socket — the idle screen, where a viewer looks first, would otherwise read `AWAITING LINK`. The endpoint returns only non-secret runtime config (model, fps, capture size, modality) and is reachable by anyone who can reach the app. The telemetry row for `detect − net` is called **Think**, not Model, now that the header names the model itself.
- **`End session` stops a run in progress** (top-right, during a scan). Before it, the only exits were completing the sequence, failing it, or waiting out the 65-second timer — every second of which is a billed Live session. Teardown is now keyed on "not SCANNING" rather than a list of end states, since the list is exactly the kind of thing a new state gets forgotten from.
- **There is a client-side mic gate, and it is OFF by default** (`frontend/public/audio-processor.js`, enable with `?gate=1`). `node scripts/gate_check.mjs` verifies its decision rule offline against the real worklet — and **two implementations have now passed every offline check and then been reported broken on a real microphone**. Synthetic signals cannot validate a gate. `?gate=1` streams the live `level` / `opens at` pair into the telemetry panel, which is what a tuning pass needs; `GATE_OPEN_RATIO` and `GATE_FLOOR_MAX` are the dials. Tuning the server's `AutomaticActivityDetection` instead only moved 0/5 to 1/5, so `realtime_input_config` stays on defaults. Timings: 250 ms pre-roll, 300 ms hangover (short on purpose — every extra ms is room noise the server's VAD hears instead of the silence that ends your turn), then ~400 ms of digital silence on close so the turn ends promptly rather than on a timeout. If it is ever turned on for real, the right architecture is `LiveRequestQueue.send_activity_start()/send_activity_end()` at the gate edges.
- **Model audio goes to the browser as binary, not base64.** The Live API's own output format is fixed — 24 kHz 16-bit PCM, and `LiveConnectConfig` has no encoding option — but the hop from backend to browser is ours, and it was base64 inside the event JSON. Measured over a 14 s session: 220 KB downlink, **202 KB of it base64 audio**, 51 KB of that pure encoding overhead — 23% of everything sent to the browser, for nothing. Audio now rides its own frame behind `MODEL_AUDIO_PREFIX` (3), shipped in the config frame like the uplink prefixes, and is stripped from the JSON so it is never sent twice. `tests/test_ws_session.py` pins both halves of that, since sending it twice doubles the cost silently and dropping the frame leaves the demo mute. Further compression (Opus, ~90% of the audio) is possible but needs a codec in the image and WebCodecs in the client — not done.
- **`index.html` and `/audio-processor.js` are served `no-store`; `/assets/*` is served `immutable`.** Vite content-hashes everything under `/assets`, so those can be cached forever — the filename changes when the content does. The entry point is the opposite: same URL, new contents every build, and it was served with only an ETag, which browsers cache heuristically. That is the likely cause of the silent-audio regression on 2026-08-13 — the backend had moved model audio to binary frames while a cached page was still running a build that only understood base64 in the JSON, producing no audio and nothing in any log. It is also why every change in this project came with "hard-refresh first". It shouldn't any more.
- **`{"type":"ping"}` is echoed as `{"type":"pong"}`** without touching the model, so the client can separate network from thinking: the HUD's `Net` row is that round trip and `Detect − Net` is the model. Measured 1–2 ms locally; the first probe of a session reads high because it lands while the Live socket is still connecting.
- **The telemetry panel's `MIC` row has three states, not two.** Every gate message is emitted from inside the gate, so with gating off — the default — nothing ever reported the mic as transmitting and the row sat on its initial `gated`: an ungated microphone pushing 256 kbit/s displayed as one sending nothing. It cost three separate "mic gated" reports before the row, rather than the gate, turned out to be the bug. `● open (ungated)` / `● transmitting` / `○ gated` now distinguish "no gate in play" from "gate currently shut".
- **`?hud=1` renders both telemetry panels with sample data and no socket**, so layout can be checked without a webcam or a billed session — which is how the panels' two overflow bugs were verified fixed rather than eyeballed. The samples are deliberately the awkward cases (long modality breakdown, four-digit tokens). The panels live in one right-hand column that owns the geometry, so they cannot disagree on width or grow into each other; a row's `detail` is its own line, because as a sibling of the value a long string widened the row past the panel edge.
- **The telemetry panel is on the main screen from page load**, not only once a socket opens. Hiding it also hid `review`, `clear`, `save` and the model name, which are wanted *before* a run more than during one. It shows real zeroes and `--` while idle, with a `live` / `idle` marker in its header so a panel of zeroes reads as "not started" rather than "broken" — and the `?hud=1` sample data is now confined to `?hud=1`, since fake figures sitting on the real main screen would be worse than no panel.
- **`review` in the Trace panel opens the whole run in-app** (`SessionReview.jsx`): uplink split into video and microphone, downlink, detect latency, capture rate, and token usage — context growth with its `image / text / audio` split plus output tokens — over the full session rather than the panels' 40-second window, plus the complete trace. It stays reachable after a round ends, since reviewing a run you have just finished is the point. `save` still writes the same record to disk for `scripts/telemetry_view.py`. Sampling into the record only happens while a socket is open — without that guard it filled with idle zeros from page load and the review opened onto a flat empty chart.
- **`scripts/telemetry_view.py` renders a recorded session.** The live panels only hold the last 40 seconds, which cannot answer "why did that run feel bad?" — the question every debugging session here has started with. Expand the Trace panel, press **save**, and the browser downloads the whole run (per-second uplink split by video/microphone, downlink, both latencies, capture rate, token growth, and the event trace); the script renders it as one HTML timeline on a shared time axis, so a spike lines up against what was happening. Offline and free — it reads a file the browser wrote. Styling is imported from `telemetry_report.py` so the two outputs stay one design.
- `Telemetry.jsx` and `EventTrace.jsx` put uplink/downlink, capture fps, latency, token usage by modality, and the event stream on screen during a session, so a bad demo is diagnosable while it happens.

- `Dockerfile` is checked in and is the source of truth. `build.sh` used to regenerate it from a heredoc on every run, silently discarding edits; it no longer does.
- **The key's project and the deployment project are deliberately different.** EAP access lives in `comglitn`, but `~/project_id.txt` stays `aisprint-491218`, so the service, image and secret stay where they always were — a key is just a string in Secret Manager, and it works fine from another project. This is a decision, not drift; `make verify`'s EAP warning is the expected noise from it. Moving the service to `comglitn` would mean a new URL, secret and image path.
- **Deploys read the API key from Secret Manager**, not from `--set-env-vars`. `deploy.sh` creates/updates the `gemini-api-key` secret from `~/gemini.key`, grants the runtime service account `secretAccessor`, and wires it in with `--set-secrets`; `cloudbuild.yaml` does the same via `_SECRET_NAME`. Never reintroduce the key as a plaintext env var or build substitution — both are readable after the fact.
- `--set-env-vars` **replaces the entire environment**, so all variables must go in one comma-separated flag. Repeating the flag keeps only the last occurrence; the old `deploy.sh` passed seven and therefore deployed only `MODEL_ID`.
- `.gcloudignore` takes full precedence over `.gitignore` for build uploads — `.gitignore`'s `.env` rule does **not** apply. `.env`/`*.key` are excluded explicitly there and in `.dockerignore`; without that, `runadk.sh`'s agent `.env` is baked into the pushed image by `COPY backend/app/ .`.
- **Model audio reaches the browser as mu-law on a binary frame (`3`), not base64 in the JSON.** The Live API's own format is fixed — 24 kHz 16-bit PCM, no encoding field in `LiveConnectConfig` — but the hop to the browser is ours, and base64 inflates binary by a third. Measured over a 14 s session: **220 KB → 95 KB**, audio itself **202 KB → 77 KB**, downlink **128 → 55 kbit/s**. `MODEL_AUDIO_ENCODING` picks `mulaw` (default), `pcm16`, or `base64` — the last being the original path and a one-variable way back if the binary path ever misbehaves. Encoder: `backend/app/audio_codec.py` (pure Python; `audioop` was removed in 3.13). Decoder: a 256-entry table in `audioStreamer.js`. **Change one and you must change the other — a mismatch is static, not an error.** Cross-checked by generating vectors with the Python encoder and decoding them with the JS table in a real browser; all 13 agreed. Opus was measured too (9.6% of PCM via PyAV, and Chrome decodes it happily) but wants a 103 MB wheel in an already-delicate install. `/audio-binary-test.html` reproduces the whole client audio path with no server, session or camera.
- Binary WS frames use a 1-byte prefix (`1` = audio, `2` = JPEG). Audio is 16 kHz PCM in, 24 kHz PCM out. The prefixes are named in `main.py` (`AUDIO_PREFIX`/`JPEG_PREFIX`) and **shipped in the `config` frame**, so the client adopts them at runtime instead of keeping a second hardcoded copy that can drift. The literals in `useGeminiSocket.js` are only a fallback.
- The input rate is not assumed. The client reports what the browser actually granted via an `audio_config` message and the backend labels blobs with that; a browser that ignores the requested 16 kHz would otherwise send 48 kHz samples tagged as 16 kHz, which the model hears as gibberish with no error anywhere.
- **The digit signal has exactly one channel: the `{"type":"match"}` frame.** The backend also forwards the raw ADK event, which still contains the same `report_digit` call — acting on both made every detection fire `onDigitDetected` twice. The client logs `functionCall` and does nothing else with it.
- A session ends when *either* the client half or the model half finishes: `asyncio.wait(..., FIRST_COMPLETED)` over `upstream_task`/`downstream_task`, then cancel everything including the heartbeat. It used to be `gather(upstream, downstream, heartbeat)`, which never completed — `heartbeat_task` loops forever — so the `finally` never ran and the **billed Live session stayed open** after the client left. The heartbeat is deliberately not a lifecycle task; with `HEARTBEAT_ENABLED=false` it returns immediately and must not end the session.
- Cloud Run deploys pass `--timeout=3600`. A WebSocket is one long-lived request, so the default 300s request timeout was a hard five-minute cap on every Live session. `--min-instances=1` keeps the ADK/google-genai import cost off the first connection.
- The video capture loop in `useGeminiSocket.js` is a `setTimeout` chain, deliberately **not** `requestAnimationFrame`. rAF is throttled to zero in a hidden or backgrounded tab while the mic AudioWorklet keeps streaming, so tabbing away silently killed video and every detection with it, on a still-open billed session. Don't "optimize" it back.
- `context_window_compression` is enabled in `RunConfig`. Without it an audio+video session is capped at **2 minutes** (audio-only gets 15), which a single demo run can reach. ADK defaults it to `None`.
- The client clears its playback queue on `interrupted`, per the Live API guidance to stop playback on barge-in. `audioStreamer.stop()` posts `{action:'clear'}` and the worklet implements it as `readIndex = writeIndex`.
- `BiometricLock.jsx` fetches an audio clip from archive.org at runtime — it fails offline or under a restrictive CSP.
- `GEMINI.md` and `.gemini/skills/live/SKILL.md` hold the Live API reference (VAD, audio formats, ephemeral tokens). Read them before changing streaming behavior.
